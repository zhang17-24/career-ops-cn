# 滴滴、百度与一次授权流程修复

## 根因

- 滴滴：独立浏览器验收只等标题，职位描述可能尚未加载，随后用正文关键词判失败。复现读到标题、地点和发布日期，但没有职责；等待职责后同一真实岗位可读。
- 百度：公开详情 HTML 含完整真实岗位，但执行站点脚本后出现 `about:blank`；旧等待标题逻辑将其混成 `navigation_error`。静态、匿名读取同一当前 URL 可核对标题和职责。尚未归因到官网中的某一段脚本，不将其解释为权限不足。
- 反复审批：SOP 和任务提示要求每次入口变化（含同域）或资源域名变化后停止；完全访问设置只负责 CLI 文件系统权限，并不修改此业务流程。
- 无法重试：相同候选指纹强制用户提供至少十字且不同的处理思路；错误任务页缺少恢复入口。

## 修改

- 页面提供显式“一次授权本候选公开招聘适配及验收后安装”。服务端持久保存后，原候选重试沿用；只允许从原企业/已批准官方来源连接的公开路线，不以候选自写字段授权。
- 托管模式允许按真实证据更新本企业路线并连续开发。旧逐次审核模式保留。仍独立验证真实数据、代码和配置完整性；登录、验证码、来源冲突及私有访问不能自动放行。
- 主动重试无需技术方案，上次平台失败原因会传给 Agent；不自动循环调用 AI。任务错误页增加恢复入口，支持只重验、不调用模型。
- 详情等待标题和职责共同就绪，使用中文区域；错误带阶段、岗位和地址。
- 仅对脚本运行后 `about:blank` 的详情增加一次当前官网静态 HTML 核验，保留域名、网络和内容检查。不是缓存、mock，也不用于绕过登录、验证码、HTTP错误或失效岗位。

## 本地验证与限制

- Web 测试 512 项通过；类型检查、构建及 `git diff --check` 通过。
- 一次授权持久化、原候选续接、异源拒绝、错误恢复及旧版保留用隔离 fixture 验证；为节省 Token，没有另启动付费 Agent 测一次授权开发流程。
- 这仍不是恶意本地代码的强沙箱。用户开启 CLI 完全访问时，候选限制还依赖可信 Agent、静态审核和独立验收，不能承诺开发零风险。
